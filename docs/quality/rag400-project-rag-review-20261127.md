## 实际运行了什么

项目提交 `5a502a384c73b164a8ca6c0c4d7bed6609867888` 的隔离文件副本，在 Docker Testcontainers 的 PostgreSQL 18/pgvector 临时数据库上执行真实迁移到 V80。使用项目 `NativeEvidenceStore` 摄取 30 份原件，经 `DocumentIngestionService` 和原生 Markdown 分块建立各 source 索引；真正调用 `KeywordRetriever → PostgresKeywordChunkSearchAdapter`，K 固定为 10。两轮之间没有改检索代码、索引配方、语料或 K。

Java 运行器只读取快照、原件、固定授权夹具和开发集无答案 query export，不读取金标。之后评分器独立读取金标与原始返回结果。测试租户映射为临时库内的 `default`；数据库隔离，未向业务库写入资料。每次结束删除自己创建的临时数据库，Testcontainers 关闭容器；构建在工作区外执行，未占用主会话 target。

这是**项目真实原生关键词检索链路评测**，不是之前的 Python BM25 模拟；也不是全链路 Agent/LLM 问答评测。没有调用模型、向量召回、重排或真实 HTTP 登录授权。权限结论仅限实际 SQL 返回结果符合固定范围，不替代平台用户权限与回读接口验收。

完整正文计分要求每个必需证据组至少有一个章节的所有非空正文行都被取到，标题命中不算。它比“只取到足以回答该问句的一句”更严格，是保守的章节覆盖指标；147/200 则只是部分正文覆盖的上界参考，不能称为完整证据召回率。当前金标定位仍到章节，尚无所有题的逐命题最小原文片段标注；两者都不是答案正确率、完整 qrels Recall 或 nDCG。范围外题未取齐两段说明，也不能据此推断模型一定错误作答。

v3 的 EASY / MEDIUM / HARD 完整正文 Top 10 分别为 39/60、42/80、28/60。按场景分别为可回答 79/140、缺证 13/30、范围外 0/10、无权限 10/10、冲突 7/10。全 200 条都执行并保留分母；199 条返回 SUCCESS，一条 EMPTY。未发现返回受限范围的块。P50 72.15 ms、P95 78.55 ms，只是一轮顺序执行、含首次冷查询效应的本地数据，不是并发或生产 SLA。

首轮的 1,985 个返回块是相同公共声明。源码 `fallbackTerms` 从左到右保留最多 16 个词项，固定前缀占掉大部分名额，实际返回也与该机制吻合。去掉评测前缀修的是测试输入，不应宣称产品检索本身提升。首轮和复跑均保留，不能只展示较好的一轮。

## 失败分析与当前边界

- 部分结果只包含章节标题，或只找到一个正文段落；不能把章节号相同当作已取到全部依据。
- 中文首 16 词项截断会遗漏后置实体。例如“关于物资借用：借用记录用什么区别两台同型号投影仪？”返回 EMPTY；业务实体位于问句后部。需要后续在项目检索器层审查词项选择，不能靠金标题目缩短或指定来源掩盖。
- 多来源必要证据经常只取到一边，其他状态相近的规则抢占名额；没有做面向当前题库的别名或金标路由补丁。
- 完整章节指标失败有一部分来自章节包含不必全部回答的相邻规则。应单独设计逐命题证据片段标注，不能直接把“部分命中”全算成功。本轮保留两个指标并明确其边界。
- 生产检索代码和主会话功能未改动。下一阶段需要词项选择、标题/正文组织与多证据召回的根因修复，以及独立语义审阅和真实模型答案/引用评分；本报告不把它们标记为完成。
