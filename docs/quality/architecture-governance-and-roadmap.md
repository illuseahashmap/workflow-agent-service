# 后端架构治理与演进路线

更新时间：2026-08-10

## 目的

本文档记录 `workflow-agent-service` 当前的架构成熟度、潜在风险、整改顺序和长期约束。它不是一次性评审结论，而是后续功能设计、代码评审和 Agent 能力建设必须遵循的工程基线。

项目当前定位为结构化的模块化单体。现有工作流、租户、权限、派单和 Agent 基础设施可以支持内部试用；生产就绪缺口以[《项目状态总览》](../status.md)和[《当前问题与后续整改》](known-issues.md)为准。

## 当前基线

- Maven 模块已划分为 `shared-kernel`、`auth-engine`、`rules-engine`、`workflow-engine`、`agent-engine`、`platform-migrations` 和 `workflow-boot`。
- ArchUnit 已约束领域层、应用层、基础设施层、REST 契约和跨限界上下文依赖方向。
- Checkstyle、SpotBugs、JaCoCo、Flyway、Testcontainers 和 GitHub Actions 已接入构建流程。
- 租户、角色、权限、登录保护、服务鉴权、流程版本、派单版本和可靠兜底命令已经具备基础实现。
- `agent-engine` 已按 Agent MVP 规格建设运行账本、状态机和 Provider 端口；完整 Agent MVP 仍需继续补齐可靠执行闭环。
- 已完成第一版 OpenAPI 全量路由覆盖、lint、兼容性和覆盖门禁；已完成 PostgreSQL RLS 纵深租户隔离、BPMN 路径解析器和任务操作支持组件。后续新增接口和仓储必须继续扩展契约与隔离测试。

## 不可破坏的架构约束

### 模块与依赖

1. `workflow-boot` 是唯一的应用组合根；业务模块不得反向依赖 `workflow-boot`。
2. 领域层不得依赖 Spring、Flowable、JDBC、Redis、Servlet 或其他基础设施类型。
3. 应用层只能通过端口访问外部能力，不得直接依赖基础设施实现。
4. 不同限界上下文不得直接访问对方的基础设施包或数据库实现。
5. `shared-kernel` 只允许放置稳定、无业务归属且依赖轻量的共享契约，不得演变成通用工具垃圾场。

### 租户与权限

1. 所有业务读写必须具有显式租户范围；不得相信客户端提交的租户标识。
2. Flowable 查询、平台表查询、缓存键、锁键、异步命令和审计记录必须使用同一个可信租户上下文。
3. 平台角色和租户角色必须保持不同授权边界；任何角色授予都必须防止自提权和越级授权。
4. 新增仓储查询时必须验证租户过滤，并为跨租户访问失败补充自动化测试。

### 事务、可靠性与数据

1. 远程调用、异步执行、重试和流程状态变更必须定义幂等键、失败状态和恢复策略。
2. 禁止使用仅存在于内存中的任务代替需要可靠交付的业务命令。
3. 所有数据库变更只能通过 `platform-migrations` 中不可修改的增量 Flyway 迁移发布。
4. 已执行的迁移文件不得重写；修正必须追加新版本。
5. 跨流程实例并发写入必须使用现有事务执行器和租户化锁策略，不得绕过。

### 安全

1. 密钥、Token、模型凭据和第三方凭据不得写入源码、日志、流程变量或普通配置文件。
2. 对外错误响应不得泄露账号存在性、密钥、SQL、堆栈或内部实现细节。
3. 自注册只能创建最低权限用户；管理角色必须由受控管理用例授予。
4. Agent 工具调用必须经过权限策略和人工确认边界，不得让模型直接获得平台管理员能力。

## 潜在问题与整改方向

| 优先级 | 问题 | 影响 | 整改方向 | 验收标准 |
| --- | --- | --- | --- | --- |
| P0 | 浏览器认证仍是自有 Token 体系 | 缺少标准会话撤销、刷新、企业 SSO、MFA 和密钥轮换能力 | 保留本地认证模式，同时抽象身份提供者端口；生产模式接入 OAuth 2.1/OIDC，建立刷新、撤销和密钥轮换机制 | 可以撤销单个及全部会话；支持标准身份提供者；安全测试覆盖过期、重放、轮换和注销 |
| P0 | 可观测性只具备基础健康检查 | 无法快速定位跨租户请求、Flowable 失败、锁竞争和派单重试问题 | 增加请求 Trace ID、结构化日志、Micrometer 指标、Prometheus 端点、告警和后台命令状态查询 | API 返回统一 Trace ID；关键业务指标可查询；失败命令可定位、告警和人工恢复 |
| P0 | 本机评审环境会跳过容器集成测试 | 数据库、Redis、迁移和真实安全链风险只能依赖 CI 暴露 | 保持 Docker CI 为强制检查，并保存测试报告；为发布分支增加完整集成测试门禁 | 合并和发布必须通过 PostgreSQL、Redis、Flowable、Flyway 和 HTTP 安全集成测试 |
| P0 | 工作流审计范围不完整 | 难以满足企业审批追责和合规要求 | 建立不可变的流程操作审计，记录发起、领取、审批、驳回、转办、终止、规则命中和管理员操作 | 每个状态变化可关联操作者、租户、时间、原因、前后状态和 Trace ID |
| P1 | 核心应用/适配器类持续增大 | 用例耦合、修改风险和测试成本上升 | 按命令、查询、参与人解析、任务操作拆分 `WorkflowRuntimeServiceImpl` 等大类；保持端口粒度稳定 | 核心类职责单一；复杂用例可以独立测试；不存在新的巨型服务 |
| P1 | 部分领域对象仍是贫血数据记录 | 业务不变量分散在应用服务和仓储实现中 | 将状态转换、规则合法性、角色授予边界等稳定规则逐步收敛为领域行为或领域策略 | 关键不变量只有一个权威实现，并有领域级测试 |
| P1 | 覆盖率门槛明显低于实际质量目标 | 新代码可能在较低覆盖率下通过构建 | 分阶段提高 `auth-engine` 和 `workflow-engine` 的行、分支覆盖门槛；优先覆盖授权、租户、并发和失败恢复 | 核心模块行覆盖率不低于 60%，关键领域策略和安全用例达到更高覆盖 |
| P1 | API 契约仍需持续扩展和版本治理 | 路由已全量覆盖，响应模型仍需细化 | 维护 `docs/api/openapi.yaml`，CI 执行 lint、Controller 路由覆盖和 PR 破坏性变更检查；逐步生成客户端类型 | 核心接口均有机器可读契约，破坏性变更在 CI 阶段被发现 |
| P1 | 租户隔离需要应用层与数据库层双重约束 | RLS 已覆盖平台业务表，但 Flowable 内部表和历史遗留表仍需按数据归属逐步评估 | `V16` 启用强制 PostgreSQL RLS；连接借用时注入租户/平台/系统 Worker 上下文；新仓储继续保留显式租户条件 | 未设置可信上下文时默认拒绝；跨租户负面集成测试覆盖核心聚合 |
| P1 | 服务间鉴权仍位于 `workflow-engine` | 安全能力扩大后会模糊工作流上下文边界 | 在网关或独立 `service-auth` 模块需求明确时迁移；迁移前不得继续向该包加入用户认证职责 | 服务鉴权与业务工作流无循环依赖，职责和发布边界清晰 |
| P1 | Agent Runtime 基础执行尚未达到生产可靠性 | 输出结果可能未经 Schema/策略校验；过期排队与失效租约无法回收；租户 Provider 存在出站风险；阻塞模型调用可能影响平台调度 | 先完成结果验证、租约续约与恢复、Provider 出站策略、独立有界执行器和对应故障测试，再接入 BPMN | 非法输出不能成功；Worker 崩溃可接管；越权网络目标被拒绝；慢 Provider 不阻塞平台任务 |
| P2 | 缺少组织、候选组、表单、通知和 SLA 等平台能力 | 工作流仍偏技术流程，企业业务落地成本较高 | 先完成任务中心、组织目录、表单模型、通知、委托、超时和升级策略，再扩展复杂流程能力 | 能用平台配置完成典型审批，不要求业务用户理解 Flowable 技术变量 |
| P2 | Agent 与 BPMN 协作能力尚未完成 | 生产可靠性基线之外，BPMN 节点、取消、人工确认和工具治理仍需完善 | 在现有 `AgentRun`、Attempt、Step、Checkpoint 和 Provider 端口上补齐流程协作闭环 | Agent 执行可恢复、可审计、可取消、可限权且不会破坏流程事务 |

## 后端实施路线

跨仓库产品阶段和业务结果以[《Workflow Agent 产品定位与目标》](https://github.com/illuseahashmap/workflow-agent/blob/main/docs/product-positioning-and-goals.zh-CN.md)为准。本节只描述后端工程实施顺序。

### 阶段 A：生产就绪基线

在开始大规模 Agent 功能前优先完成：

1. Trace ID、结构化日志、指标、告警和失败命令运维入口。
2. 完整流程操作审计和安全审计查询能力。
3. 前后端 OpenAPI 契约、路由覆盖与兼容性检查。基础门禁已完成，后续持续细化响应模型。
4. 强制容器集成测试、发布校验和覆盖率提升。
5. 标准身份提供者接入方案、会话撤销和密钥轮换设计。
6. 持续扩展 OpenAPI 响应模型，并将破坏性变更检查纳入发布流水线。

### 阶段 B：工作流平台完善

1. 拆分运行时大类，明确命令、查询和领域策略。
2. 建立组织、候选组、任务中心、表单、通知、委托、SLA 和升级机制。
3. 完善租户纵深隔离、数据导出、归档、备份和恢复方案。
4. 建立流程定义、派单规则和表单版本之间的显式兼容关系。

### 阶段 C：Agent Runtime 生产闭环

Agent 基础领域与管理链路已经实现。只有阶段 A 的安全、审计、可观测性和可靠性基线完成后，才继续完成生产闭环：

1. 补齐输出 Schema/结果策略、租约续约与接管、取消、超时和故障恢复。
2. 完成 Provider 出站策略、凭据轮换、独立有界执行器和租户公平调度。
3. 受治理的工具注册、输入校验、权限策略、人工确认和幂等调用。
4. 通过 BPMN 事件或可靠命令与流程交互，禁止在 Flowable 事务内执行长时间模型调用。
5. 完成 Token/成本预算、检索证据、Guardrail、完整执行审计和故障注入测试。

### 阶段 D：人机协作与设计时生成

1. 实现自主 Agent 节点，并为 User Task 建立绑定、任务激活标识和版本化自治策略。
2. 按[《证据驱动的 Agent 渐进式自治设计方向》](../architecture/evidence-governed-agent-autonomy.md)先实现 `SHADOW` 和 `ADVISORY`，形成 Agent 建议、人工决定、最终决定和后续结果的决策证据。
3. 建立历史任务回放、AgentVersion 对比、最小评测集、人工审批升级和只减权的安全降级机制，再逐步开放 `SUPERVISED` 与受约束自动完成。
4. 建立知识与工具端口、运行诊断和跨制品证据关联能力。
5. 冻结流程语义 IR 和 `CollaborativeProcessDraft`，再实现骨架生成、细节填充、确定性 BPMN 编译与测试。
6. 生成器只创建草稿，禁止绕过部署校验、权限和人工发布门禁。

## 变更完成标准

后续任何非文档变更至少必须满足：

- 明确所属模块、限界上下文和依赖方向。
- 明确租户、权限、审计、幂等、事务和失败恢复影响。
- 数据库变更包含新的 Flyway 迁移和迁移集成测试。
- 新业务规则包含单元测试；跨基础设施行为包含集成测试。
- `mvn verify` 通过，且不得通过降低规则或覆盖率门槛规避失败。
- API 变更同步更新契约、前端类型、错误码和兼容性说明。
- 不记录敏感数据，不引入默认生产密钥，不绕过已有安全过滤链。
- 大型功能先更新架构文档和决策记录，再开始实现。

已确认并完成整改的历史问题见[《已知问题与整改计划》](known-issues.md)，Agent 领域的初步边界见[《Agent 协作架构设计》](../architecture/agent-collaboration-design.md)。
