# 后端架构治理基线

更新时间：2026-08-18

本文属于“长期设计”，只保留不可破坏的工程约束。当前进度以[下一步计划](../status.md)为准，缺陷以[待修复问题](known-issues.md)为准，不在本文重复维护整改清单。

## 一、模块与依赖

1. `workflow-boot` 是唯一应用组合根，业务模块不得反向依赖它。
2. 领域层不得依赖 Spring、Flowable、JDBC、Redis、Servlet 或其他基础设施类型。
3. 应用层只能通过端口访问外部能力；基础设施实现不得向上泄漏。
4. 限界上下文之间通过稳定 DTO、应用端口和事件协作，不直接访问对方基础设施包或数据库实现。
5. `shared-kernel` 只保存稳定、无业务归属的共享契约，不演变为工具类垃圾场。

## 二、租户、权限与安全

1. 所有业务读写必须绑定可信租户上下文，不能信任客户端提交的租户标识。
2. 应用层显式租户过滤、连接级上下文和 PostgreSQL 强制 RLS 必须同时存在。
3. 缓存键、锁键、异步命令、审计记录和 Flowable 查询必须使用同一个租户边界。
4. 平台角色与租户角色分离；自注册只能创建最低权限用户，管理角色必须由受控用例授予。
5. Token、模型凭据和第三方密钥不得写入源码、日志、流程变量或普通响应。
6. Agent 工具、流程终止、权限变更和外部写操作必须经过权限、风险和人工确认边界。

## 三、事务、可靠性与数据

1. 远程调用、异步执行、重试和流程状态变更必须定义幂等键、失败状态和恢复策略。
2. 不能用仅存在于内存的任务或信号量替代可靠业务记录和跨实例治理。
3. 数据库变更只能通过不可修改的增量 Flyway 迁移发布。
4. 已执行迁移不得重写；修正必须追加新版本。
5. 跨流程实例并发写入必须使用现有事务执行器和租户化锁策略。

## 四、质量门禁

- API 变更必须同步更新 OpenAPI、错误码、响应模型、前端类型和兼容性检查。
- 新业务规则必须有领域/应用单元测试；跨数据库、Flowable、Redis 或 HTTP 的行为必须有集成测试。
- 代码必须通过 Maven Enforcer、Checkstyle、SpotBugs、JaCoCo、ArchUnit 和 CI 检查。
- 生产能力不得以降低覆盖率、关闭安全检查或绕过测试来“修复”。

## 五、变更完成标准

任何跨模块功能在实现前必须明确限界上下文、依赖方向、租户/权限、审计、幂等、事务和失败恢复影响；实现后必须更新[下一步计划](../status.md)或[待修复问题](known-issues.md)，而不是留下新的重复路线文档。
