# 工具超时、撤权的持久收尾与 P-17 验收

2026-11-27；位于 `codex/v79-route-p17` 独立工作区。基线 `7064e9f`，本轮新增 V81，不引入 V80 的租户容量配置或管理功能。

## 已修复的行为

- 工具边界复用既有 AgentFailureMapper，将 MCP 故障转换为稳定的类型化错误。可重试错误返回 TOOL_TRANSIENT；确定不可继续或预算耗尽时，先提交持久停止，再返回 RUN_STOPPED。Python 现有 STOPPED 投影清空候选引用；终态由既有 Java 收尾服务完成，无须模型或 ACK。
- 新 v2 Run 冻结每个稳定工具 intent 最多 **2 次物理尝试（含首次）**。历史 v2 Run 以原 physical_limit 回填，不重置已经消费的调用，不突然缩小其既有上限。总 Run、工具、账户及全局容量限制继续共同生效。当前策略是平台冻结默认值，尚未增加租户配置界面。
- 每条工具失败绑定真实 call_attempt_id、operation、请求摘要、generation 和 Run，错误只保存稳定代码。重复上报不能重复计数，也不能因为后续调用已开始而误停 Run；错误内容冲突拒绝写入。旧代次不能写入停止裁决。
- 工具执行、历史回执重放、模型/摘要/READ_RESULT/最终验收前后的证据授权均沿用当前权限检查；发现撤权后持久停止。重新授予权限不能复活已停止的 v2 Run，需经治理创建新 Run。旧 schema v1 和原生路径保留原预算、Attempt 和恢复行为。
- Run/Attempt 终态和完成 Outbox 仍在同一事务提交；停止裁决独立持久化。Outbox 故障不能重新启用执行，重启后重试收尾，重复收尾只发布一次。沿用实际 Flowable 失败策略进入人工复核，没有由测试或模型直接创建人工任务。

## 容量与未知调用

超时不证明远端调用已结束，原许可保持 QUARANTINED 并计入全部容量限制，不伪造 RETURNED，也不退款。只有绑定可信失败账本的可重试只读工具调用，才允许申请下一枚独立许可；没有已知失败的未知调用仍阻塞同 intent，容量不足仍等待。新许可同样消耗 Run 与 intent 预算。

V81 将 `graph_call_inflight` 的唯一约束范围收紧为 ACTIVE；已有容量锁内的 pending 检查继续阻止未经失败确认的重发，所有非 RELEASED 许可仍参与配额计数。一个 intent 可以保留多个已失败但物理结束尚待确认的隔离许可，不能据此认为未知调用对账已完成。本轮不支持有副作用工具自动重试。

## 验收及证据

图端 P-17 和原生 P-17 均已 **7/7**。七项均使用同 Run 的检索、调用、终态和实际 Flowable 去向评分。超时场景是一个业务 Attempt、同一稳定工具 intent、两个不同的物理尝试 UUID；撤权场景无后续模型或订单调用，最终人工复核。

新增评分字段 `physicalAttempt`，以持久调用/失败记录与独立订单观察逐条核对，不能拿两行重复逻辑审计充当两次重试。仍兼容旧原生 trace v1；原始证据缺件、串 Run、重复物理 ID 或缺少真实超时记录均不通过。没有改金标或降低七场景要求。

本次图端入口已使用真实容量封装、Java Gateway、Python LangGraph、PostgreSQL checkpoint 及 Flowable。模型仍为确定性脚本，MCP 远端仍为进程内只读夹具；这不代表真实 Provider/MCP 传输、生产派发负载或整个 G1/G2 已通过。历史 5/7 的现场保留在[初轮记录](graph-p17-node-acceptance.md)。最终批次、测试与评分见[机器证据](evidence/p17-durable-stop-20261127.json)。

## 迁移与后续

V81 独立于 V80，未修改任何旧迁移。应用前停止图宿主并按既有流程执行事务迁移；回填显式开启事务级 system worker 可见性，覆盖 FORCE RLS 下的历史租户行。新表启用 FORCE RLS 和不可变触发器。测试使用专用临时数据库，本轮未升级业务数据库；合并发布时仍须验收包含另一工作 V80 的完整迁移序列，不可把隔离分支的缺号迁移当作完整生产升级结果。

下一步继续同租户双采购、连续两次压缩、换代恢复与迟到写隔离的组合验收。生产真实外部调用、未知调用对账、取消/暂停运维及发布排空仍开放；业务版本尚未切换，不能删除旧执行器。
