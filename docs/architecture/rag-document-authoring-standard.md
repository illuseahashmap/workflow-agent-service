# RAG 企业知识文档编写与多模态扩展规范

状态：文档编写规范草案；多模态摄取能力尚未实现
编制日期：2026-10-17
适用：十领域测试语料及后续经审核的租户知识源

## 1. 为什么现在定义

知识文档不仅供人阅读，还要成为可授权、可版本化、可引用和可评测的证据。目前仓库的 `TextChunker` 只把 UTF-8/Markdown 文本按长度和换行切分；它不会理解表格的行列关系，也不会读取 Markdown 图片中的像素。现阶段上传单个 Markdown 文件，**不能**据此宣称其引用的图片、PDF 或复杂表格已被可靠检索。图文混排、OCR、复杂表格和多模态 Embedding 是后续能力，本规范先冻结内容和证据边界，避免日后迁移时重写全部语料。

## 2. 文件和版本契约

每份文件只对应一个稳定 `documentCode` 和一个不可变内容版本；已发布内容不得原地改写。至少记录：标题、领域、owner、reviewer、审批和生效时间、状态、适用主体、`knowledgeScope`、敏感级别、所替代版本、正文哈希、附件清单和维护计划。当前测试文档保留 `DRAFT` 标识，只有实际审核后才能填写批准人、发布日期并进入已发布索引。`approvedAt`、`effectiveFrom`、业务事实发生时点和入库时间不可混用。

正文使用稳定、不可复用的章节号，如 `PROC-POL-01 §3.1`。定义、规则、例外、步骤、输入材料、状态以及纠错渠道分别成节。关键阈值必须写出开闭区间和单位；“及时”“必要时”“适量”等词如会影响决策，必须定义触发条件或明确由谁人工裁量。每个规则都标明适用范围、前提、结论、例外及证据来源；FAQ 和案例只能解释规则，不得新增隐含政策。

### 目录和资产

采用 `docs/fixtures/knowledge/domains/<domain>/<documentCode>.md` 保存正文；同文档的自有媒体放入 `assets/<documentCode>/<assetId>.<ext>`。资产具有稳定 `assetId`、相对路径、MIME、内容哈希、版权/来源、描述、敏感级别、所属 `documentCode/version`。不使用公网热链、不嵌入真实员工或客户照片、不复制受版权保护的第三方图表。发布时正文和资产作为**同一文档版本快照**校验，缺失、哈希不匹配或越权资产会阻止发布；删除和撤权必须同时覆盖原文与派生文本/图片索引。

## 3. 何时用表格、图和截图

| 信息形态 | 优先表达 | 加入条件 | 不允许 |
| --- | --- | --- | --- |
| 阈值、角色矩阵、条件对照 | 简单 Markdown 表格；正文先陈述决定性规则 | 行列关系确实帮助比较，列头、单位与边界清晰 | 用表格排版；把唯一的关键结论埋在图片中 |
| 多步骤和分支 | 有编号的文字步骤 + 可选流程图 | 分支/回退多于线性文字能清楚表达的程度 | 图里有独有审批条件、文字没有对应条款 |
| UI 操作 | 稳定控件名称和文字步骤；必要时辅以截图 | 控件位置不易描述且版本可固定 | 只写“点击图中红框”，不记录软件版本 |
| 组织/系统关系 | 实体与关系文字清单 + 可选示意图 | 图能显著降低理解成本 | 让图代替可信组织数据、权限或正式合同 |
| 外部票据/合同样例 | 人工合成、去标识化的结构化样例 | 文字无法表达版面特征，且权利与敏感性已核验 | 上传真实发票、签名、证件或密钥 |

表格前必须有编号和用途，例如“表 1：普通办公采购审批路径”，列名体现单位及适用条件；不跨行/跨列合并出只有视觉才能理解的表头。关键规则在紧邻的文字中再完整表达一次：这不是冗余填充，而是当前文本切分、窄屏显示和辅助技术读取的保底。复杂表格应拆为多个简单表。W3C 的[表格可访问性指南](https://www.w3.org/WAI/tutorials/tables/)强调表头与数据单元格的可识别关系，且不建议将数据表格用于布局；这里的 Markdown 表格仅适合简单结构，未来 HTML/PDF 导出需保留表头语义。

图片必须有**短替代文本**、相邻的图题及可独立理解的长文字说明。流程图的说明须列出所有节点、边、条件、回退路径和异常出口；数值图须在正文/表格给出精确数值及单位。颜色、箭头位置或像素不能成为唯一证据。W3C 的[复杂图像指南](https://www.w3.org/WAI/tutorials/images/complex/)同样要求短说明与详细文本表示。使用 SVG 时保留可审查源文件，不以带脚本 SVG、外链字体或外部资源作为知识资产；未来发布端需进行 MIME、尺寸、内容和脚本安全校验。

## 4. 现阶段可执行规则与未来摄取目标

**当前阶段：** 仅承诺 Markdown 正文中的文本可进入现有摄取链路。简单表格可写入 Markdown，但按普通文本处理；标题/行列对应关系、图像像素和附件都**没有结构化解析保证**。高风险回答必须引用正文规则段落，不得只引用被切断的单个表格行或图片链接。编写者可在文档中提供图示，但测试入库前必须用不依赖图示的文本通读一遍；现有上传入口对相对资产也不保证打包和解析。

**扩展阶段的目标对象：**

```text
DocumentVersion (不可变正文 + 资产清单)
  ├─ TextSection {sectionId, headingPath, offsets, text}
  ├─ Table {tableId, caption, headers, rowIds, cells, contextSectionId}
  └─ Figure {figureId, mime, assetHash, alt, longDescription, contextSectionId}
        → 统一 EvidenceReference {documentVersion, locator, fingerprint}
```

表格的 `locator` 应能定位表/行/列或单元格，图像定位 figure/页码/区域；现有 `ChunkEvidence` 保持兼容，新增 `TableEvidence`、`FigureEvidence` 应通过中立 Evidence 契约承载，不向领域层泄漏 OCR 或厂商返回类型。OCR/视觉模型生成的文字必须标为**派生描述**，保存模型/解析器版本、置信/异常信息及原始资产引用；不得与人工审核的正文混作同等权威。多模态向量可用于召回，但回答仍要落到有权限的原始文档版本与明确 locator；低置信、表头丢失或跨页断表时拒答/转人工。

摄取应先做内容类型、文件大小、页数/像素、压缩包、恶意内容和租户配额检查；正文、附件、派生文本及向量遵循相同租户/RLS 和知识范围。解析任务与索引版本绑定，可重试、可撤销；发布时需要验证文字与图表的引用解析成功。检索 Trace 记录原始资产/表 ID、解析器与模型版本、授权过滤、命中证据和最终引用，不能只存图片摘要。产品 API/前端要能显示“此结果含尚未解析的图片/表格”，不能误报为完整知识覆盖。

上述对象是**扩展目标，不是当前已实现接口或数据表**。引入之前先用含合并表头、跨页表、失真 OCR、截图旧版本、图中隐藏指令、越权图片和资产删除的固定评测集验证收益及安全。

## 5. 编写和发布检查单

1. 正文单独阅读是否能复述规则、例外和失败处置？如果不能，图片/表格的文字等价内容不足。
2. 所有阈值是否有单位、边界、计算口径和恰好等于阈值的例子？
3. 图、表、截图是否有稳定编号、来源、版本和不依赖颜色的说明？
4. 文字、表格和图片有无相互矛盾的旧值？同文档内矛盾不得通过“取最新一处”解决。
5. 资产是否与正文一起冻结、授权和可删除？是否含敏感凭据、真实个人信息或不明版权？
6. 引用能否定位到 `documentCode/version/sectionId`，后续图表能否细化到行/图区域？
7. 对未实现的解析能力是否明确标注限制，并在评测中期待拒答而非猜测？

仅当以上检查与业务审核完成，才可将草稿升为已发布知识。正文制作进度和技术能力完成度分别报告，不能以“文档包含图片”推断“RAG 已支持图片”。
