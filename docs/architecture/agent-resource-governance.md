# Agent 资源治理、虚拟线程与租户公平调度设计

状态：长期设计，尚未实现  
更新时间：2026-08-15

本文档记录 Agent 执行规模扩大前必须遵守的资源治理约束。它不是当前能力声明；实现状态以 [项目状态总览](../status.md) 为准。

## 一、问题与当前基线

多租户系统需要同时解决两类隔离：

1. **数据与权限隔离**：防止跨租户读取、修改和越权。当前通过租户上下文、显式过滤和 PostgreSQL 强制 RLS 建立基础纵深防御。
2. **计算资源隔离**：防止单个租户、Agent 或 Provider 占满执行槽位、队列、连接、Token 和费用预算。当前尚未闭环。

当前 Worker 使用固定大小、有界队列的模型执行池，默认单实例并发为 2、队列容量为 20。`2` 是开发阶段的保护性默认值，不是租户套餐，也不是长期容量模型。当前实现只能限制单实例总并发，不能保证跨实例租户公平。

## 二、必须遵守的设计原则

### 1. 共享基础设施，逻辑隔离资源

不得为每个租户永久创建独立线程池、调度器或数据库连接池。租户数量增长后，这种设计会产生大量空闲资源和不可控的运维成本。

默认采用共享执行基础设施，并通过分层配额和公平调度建立逻辑隔离：

- 平台全局并发和队列上限。
- 租户保底容量、可借用容量和硬上限。
- Provider 并发、RPM、TPM 和熔断边界。
- Agent 定义或版本级并发上限。
- 租户 Token、费用和时间窗口预算。
- 管理任务、恢复任务与普通模型任务的资源预留。

只有监管、合规、专属部署或大型客户明确要求时，才升级为独立 Worker、独立队列或独立基础设施的物理隔离。

### 2. 公平调度必须是 work-conserving

公平不等于静态切死资源。目标策略是“保底 + 借用 + 硬上限”：

- 每个租户获得最低保障，避免饥饿。
- 其他租户空闲时，活跃租户可以借用剩余容量。
- 租户不得超过自身硬上限和平台全局上限。
- 容量紧张时按权重、优先级和等待时间恢复公平分配。
- 不抢占已经发出的模型调用，只约束后续领取。

单纯按 `created_at` 或主键顺序领取不能保证租户公平；长期领取算法必须显式考虑租户、Provider、优先级和可用许可证。

### 3. 虚拟线程只解决阻塞成本，不提供资源隔离

模型 HTTP 调用以网络等待为主，适合在验证兼容性后迁移到 JDK 虚拟线程。虚拟线程可以降低大量阻塞调用占用的平台线程成本，但不得被视为无限并发能力。

采用虚拟线程后仍必须保留：

- 全局、租户、Provider 和 Agent 并发许可证。
- 有界排队和明确拒绝/背压策略。
- Provider 限流、超时、熔断与重试预算。
- 数据库和 HTTP 连接资源边界。
- 响应体、上下文和内存预算。

禁止直接使用无约束的“每任务一个虚拟线程”替代当前有界执行边界。虚拟线程负责承载调用，资源治理策略决定调用是否有资格开始。

### 4. 分布式配额不能只依赖本地 Semaphore

本地信号量只对单个 JVM 有效。部署多个 Worker 后，租户实际并发是所有实例之和，因此跨实例配额必须有共享协调状态。

目标职责划分：

- PostgreSQL 保存租户套餐、配额配置、AgentRun 和审计事实。
- Redis 或等价协调层承载高频分布式并发许可证、RPM/TPM Token Bucket；许可证必须有 TTL，并与 Run、Attempt 和租约所有者关联。
- PostgreSQL 运行账本作为最终事实，后台任务定期校正协调层的漂移。
- 协调层不可用时默认停止领取新的模型任务，不影响已有人工工作流；是否允许降级必须由显式策略决定。

配额配置必须版本化、可审计，并支持平台默认值、租户覆盖和 Provider 覆盖，不能散落为代码常量。

## 三、租约续约的长期方案

当前实现由单实例共享的一个调度线程为活跃 AgentRun 注册心跳任务，每隔租约时长的三分之一续约。它不会为每次模型调用创建一个平台线程，但串行数据库续约存在头阻塞风险：某次续约异常缓慢时，可能推迟后续租约。

短期增强方向：

- 使用固定大小、受限的共享续约执行器，而不是每个 Run 一个线程。
- 设置严格的数据库获取连接、事务和语句超时。
- 保留至少两次续约机会的安全余量。
- 续约失败立即使本地 LeaseHandle 失效，旧 Attempt 禁止提交结果。

规模扩大后的目标方案是集中式租约管理器：

1. 活跃 Run 只登记到本地租约注册表，不持有独立心跳线程。
2. 固定调度任务扫描即将到期的租约。
3. 按租户或分片批量续约，避免 N 个独立定时任务和 N 次串行往返。
4. 续约条件必须包含租户、Run、Attempt、lease owner、当前状态和 Deadline。
5. 批次中的失败必须精确反馈到对应 LeaseHandle。
6. Recovery 继续使用数据库租约和 `SKIP LOCKED` 接管真正失效的 Attempt。

虚拟线程不用于“每个 Run 启动一个循环心跳”。它可以承载受限的阻塞续约任务，但不能代替批量续约、数据库超时和租约所有权条件。

## 四、目标执行链路

```text
AgentRun 进入可执行队列
        ↓
公平调度选择租户与 Run
        ↓
依次申请全局、租户、Provider、Agent 许可证
        ↓
领取 Run 并创建新 Attempt/租约
        ↓
虚拟线程执行模型调用
        ↕
集中式租约管理器批量续约
        ↓
结果校验、业务策略和状态提交
        ↓
释放许可证并记录用量、成本和审计
```

任何阶段失败都必须保证：许可证最终释放、旧 Attempt 不能覆盖新 Attempt、租约过期可恢复、重试受预算限制。

## 五、指标与验收

至少需要以下低基数指标：

- 全局及按受控维度聚合的运行中、排队、拒绝和积压数量。
- 许可证等待时间、获取失败和借用容量。
- Provider RPM、TPM、429、超时、熔断和延迟。
- 租约续约耗时、批次大小、续约失败、失效接管和迟到结果。
- 租户预算消耗、超限拒绝和降级次数。

租户 ID 不应无约束地作为 Prometheus 高基数标签；租户明细进入审计/查询存储，指标平台只保留受控维度或 Top-N 聚合。

验收必须覆盖：

- 单租户不能长期占满全部执行容量。
- 空闲容量可被其他租户借用，不能因静态分片浪费。
- 多实例下全局租户并发不超过配置上限。
- 慢 Provider 不阻塞其他 Provider、Recovery 和平台安全任务。
- Worker 强杀、协调层短暂不可用和租约续约延迟后可自动收敛。
- 旧 Attempt 的迟到响应不能提交，许可证不会永久泄漏。

## 六、推荐实施顺序

1. 建立版本化资源策略模型和只读决策端口。
2. 改造领取查询，实现按租户/Provider 的 work-conserving 公平调度。
3. 实现带 TTL 和 fencing 信息的分布式许可证及对账恢复。
4. 将模型阻塞调用迁移到虚拟线程，同时保留全部并发和背压边界。
5. 将逐 Run 定时续租升级为集中注册、分片或批量续租。
6. 补充故障注入、压力测试、容量基线、告警和运维手册。

在前 3 步完成前，不以提高线程数或启用虚拟线程的方式扩大生产并发。
