# Agent 资源治理、跨实例配额与公平调度

状态：V67 治理组件与 V68 全平台准入已实现；认证派发宿主、有界 Worker CLI、共享账户配置/审计已接通并默认关闭图宿主。最终业务接纳、完整节点等价和整个平台容量验收仍开放。操作配置见[部署手册](../operations/graph-dispatch-host.md)。

更新时间：2026-11-12

2026-11-27 方案补充：第五节新增 Token 用量配额、发送前预留与返回后结算设计，当前待实现。v2 已有 Run 调用次数、deadline、持久停止及无模型收尾；Token 记录不等于 Token 硬限额，具体历史实现边界见[预算与停止验收](../quality/graph-v2-budget-stop-regression.md)。

执行权威与 G0–G3 以[LangGraph 接入设计](langgraph-runtime-adoption-design.md)为准。本文只定义平台治理，不自研图节点调度、内部 Checkpoint 或第二套恢复游标。当前实现及验收记录以[状态页](../status.md)为准。

## 一、已核对的现状

- Java 原生 Worker 使用固定、有界执行池，默认并发 2、本地队列 20；排队的是领取操作，不是大量已领取租约的 Run。每个执行槽仍可能连续跑完整 Run。
- 当前领取查询先 COUNT(RUNNING) 再锁候选；并发事务可锁不同 Run 且同时看到余量，因此不是严格的跨实例租户硬配额。
- MCP 出站已有 Redis 租户令牌桶、并发硬上限和连接器熔断。它不等于全平台、模型供应商和图执行的公平容量控制。
- 原生 Run 心跳已有共享有界调度池、活动注册硬上限及指标。开源图模块已用同会话 advisory lock + 官方 saver 保护图持久化；商业服务的任务队列/租约不在本方案内。平台继续承担业务命令与资格，不再以原生 nextStep/Recovery 驱动同一图。

## 二、治理分层

| 层次 | 平台负责 | 不能混淆的边界 |
| --- | --- | --- |
| 业务准入 | outstanding 上限、输入/历史体积、deadline、幂等提交 | 入库速率不是运行吞吐，PAUSED/WAITING 也占存储配额 |
| 图启动/恢复资格 | 按租户公平放行、后台管理预留、队列背压 | 只记录线程是否有资格运行，不保存下一节点 |
| 模型/工具调用 | 全局/租户/供应商账户模型/连接器额度、速率、费用 | 两个 Provider ID 共用账户不能各自获完整供应商额度 |
| 图内部执行 | 复用 LangGraph 推进/恢复；外围只保护图实例所有权和执行上限 | Java 不领取内部 Step，OSS 图库不提供平台公平队列 |
| 本机资源 | 有界虚拟线程/异步客户端、CPU 池、连接池、响应体上限 | 本地 Semaphore 不是跨实例硬配额 |

共享资源、逻辑隔离，不为每个租户永久创建线程池或连接池。配额按版本化策略支持平台默认、租户覆盖、Provider 覆盖，并记录生效/审计。专属物理隔离只在明确合规或容量需要时启用。

## 三、平台准入与调用许可权威

目标采用 PostgreSQL 保存平台 outstanding、调用 Permit、预算预留及结算事实；这些**仅是平台治理数据，不含图任务/检查点**。Run 创建与 outstanding 占位同事务，先查业务幂等，终态只释放一次。未终态 Run 的图恢复不重新申请业务队列位置；终态运行已经释放占位，人工重试必须同事务重新准入，不能绕过全局上限。

调用许可按固定资源键顺序短事务锁定全部所需额度；任何不足整笔回滚，不持有部分额度等待另一额度。Permit 绑定 tenant/run/operation/session generation/claim token，所有续约、释放、结算带条件并检查影响行数，不能无条件 counter--。策略缩容不抢断已发请求，停止新申请并排空。运行服务的领取与平台许可**不是跨库原子事务**：先到治理 Gateway 获准才可真正出站，不能把 backendRun 启动等同已获得 Provider 额度。

现有 MCP Redis 并发机制在统一切换前保持；切换以版本化治理入口为单位，明确哪一侧是硬并发权威，禁止新旧重复扣减。Redis 可继续承担速率和熔断；多 key 原子性须符合部署拓扑，不能假定 Cluster 跨槽 Lua 原子。发送未知时预算/速率消耗保守保留，不因本地失败自动退款。数据库保存调用/用量事实用于对账。

Permit ACTIVE 在确定完成后转 RELEASED；请求可能仍在远端执行则转 QUARANTINED，继续计入上限，待确定取消/完成或有依据的远端最大执行期限后释放。无法核实的写操作转人工，不能凭 TTL 无限重发。fencing 拒绝本地旧提交，不承诺外部 exactly-once。

协调层不可用时停止依赖它的新调用，不把本地缓存提升为无约束备用权威。对账修复异常，不代替正常路径的原子硬上限。

## 四、公平分配与持久等待

按活跃租户的权重、硬上限和等待老化分配启动/调用资格，空闲额度可借用；不抢占已经发出的模型请求。只按 created_at 选 Run 或依赖 runtime 的线程互斥不能证明租户公平。

公平队列状态须跨实例协调，不能每实例各算全局额度。候选扫描有界并记录进度，跳过资源封禁的租户继续其他可用租户，避免头部阻塞。优先级有占比上限；恢复/管理流量有预留且不能饿死普通任务。最低保障以依赖资源可用、未超硬上限为前提，不承诺超售保底。

资格不足时 Gateway 返回稳定 waitRequestId、原因和 nextEligibleAt；图持久挂起，释放执行资源。平台只维护线程/调用资格等待项，runtime 决定其恢复节点。图挂起与平台登记的先后竞态、resume 重复/丢失通过幂等命令、持久状态查询和扫描处理，不靠内存通知。资格短期预留应过期回收，图恢复后重新验证；不能先拿着稀缺 Provider 许可在 runtime 队列里长时间排队。

该集成必须在 G0/G2 验证真正释放运行槽以及有界等待；若所选部署没有安全扩展点，需要调整部署方案，不能在 Java 偷建图任务调度器。拒绝忙循环或为等待每次调用永久保留线程、连接和租约。

手动/API 超额给明确 429/503 和可操作原因；Flowable 节点创建 Run 的准入失败需回滚本次推进事务，走原有有界失败/运维路径，不能先激活等待节点再丢失 AgentRun。已准入的业务等待不重复创建新 Run。

## 五、执行、租约和预算

无进展与防循环的目标契约见 [LangGraph 接入方案 §5.1](langgraph-runtime-adoption-design.md#51-无进展检测与防循环2026-11-16待实现)：SliceBudget 可按片段重置，Run 的逻辑/物理调用、Token/费用及纠偏机会不可因 resume、Attempt 或旧 Checkpoint 回放重置。预算耗尽必须可无模型收尾；未知外呼许可不随业务终态自动释放。该契约待实现，不能将现有容量 Permit 或 maxSteps 当作完整预算账本与语义防循环。

### Token 用量配额（2026-11-27，待实现）

**现状与目标。**当前 v2 已落地 Run 模型/工具调用次数预算、不可逆停止与无模型收尾，deadline 覆盖整个运行，执行片段另有时间/次数预算；已收到的 input/output Token 可落账，但尚无完整的发送前 Token 预留和严格限额。以下方案在这些限制之上增加 Token 预算，不以 Token 替换 deadline、调用次数或并发容量，也不把“耗时”换算成 Token。

**额度分层与配置。**

| 范围 | 计划控制项 | 生效与归属 |
| --- | --- | --- |
| 单次模型请求 | 输入上界、最大输出 Token | Java 根据最终请求计算/验证，输出上限由 Provider 适配器实际传递并验证支持能力 |
| 整个 Run | 累计 Token 总预算，可另设输入/输出子上限 | Run 准入时冻结预算策略版本；所有 Attempt、恢复、模型角色和真实重试共享 |
| 租户计量周期 | 周期 Token 总配额 | 平台默认、租户覆盖；周期类型、时区、边界和策略版本明确，不因进程重启清零 |
| 平台/共享 Provider 账户 | 可配置的周期或速率约束 | 按可信账户资源键汇总；不同 Provider 配置共用账户时不能重复获得额度 |

单 Run 配额由 Agent/平台预算策略确定；租户周期配额放在平台管理员的租户资源配额页面，展示继承值、覆盖值、周期、已结算、预留、未知用量占位及剩余额度。字段名称和 API/数据库迁移在实施时评审，不表示现有页面已有这些控件。租户不能自行提高平台上限；降低额度不抹除历史消耗，也不强杀已发出的调用。额度追加或人工调整须走独立授权和审计，不能自动解除已持久停止的 Run。

**计量口径。**首版按版本化口径累计模型输入和输出 Token，不把 Token 数等同金额。缓存输入、推理 Token 等可能是输入/输出总数的子集，必须由 Provider 适配器明确归一化，禁止直接把所有 usage 字段相加造成重复计费。Provider 原始 usage 与归一化值均保留；不同模型的费用差异由以后独立的计价策略处理。旧记录中的 0 不自动解释为真实零消耗。

用量至少区分 `REPORTED`（Provider 报告）、`ESTIMATED`（有版本化方法的估算）、`UNKNOWN`（缺失或无法确认）。未返回 usage、超时或连接断开不能按零结算。账面必须区分已结算消耗、未结预留、未知消耗占位；未知占位由预留转换而来，不能既保留预留又重复加算一次占位。

**请求生命周期：先预留，再发送，最后结算。**

1. Java 在最终消息、工具 Schema 和上下文组装完成后计算可信输入上界，加上本次受控最大输出，形成预留量。不能只数用户问题，也不能用随意字符比例冒充精确 Token。Provider 特殊消息包装、多模态、推理输出和缓存口径必须在适配器能力契约中说明。
2. 真正出站前，在数据库短事务内以固定锁顺序检查并预留 Run、租户及适用共享资源额度：`已结算 + 未结占位 + 本次预留 ≤ 上限`。各维度原子成功或全部回滚，不能持有半份额度等待另一份；不得与现有 Permit/Run 锁序形成反向依赖。并发分支争抢最后一份额度，只允许获准者发送。
3. 预留绑定 tenant、run、operationId、物理 callAttemptId、策略版本及周期 bucket。结合已有物理发送事实记录发送状态，不在数据库事务中等待网络。相同操作的回执重放不重新扣减；同一操作如果确实再次发送，则是新的物理尝试，必须重新预留，未知旧尝试不自动退款。
4. 收到可信 usage 后幂等结算实际量并释放差额。输入估算失准导致实际量超过预留时，必须记录真实超额而非截断账单，阻断后续出站并告警；不能宣称此时仍保证绝不超限。晚到 usage 可在 Run 终态后补账，但不能复活运行或改写业务结果。
5. 能证明尚未发送且已建立发送屏障的请求可释放预留；发送结果未知则保留占位，待可信回执或受审计对账处理。业务停止、租约到期、容量 Permit 释放都不是 Token 退款依据。

只有在输入上界可信、Provider 确实强制输出上限且所有出站均受控时，才能承诺严格 Token 硬上限。否则只能启用明确标注的保守估算模式，或拒绝该模型用于要求严格预算的任务；不能把“返回后发现超限才停止”宣传成发送前硬限额。未知量的上界也不可信时须阻断后续相应调用，不能凭经验释放额度。

**覆盖范围与责任。**Java 是配额权威，LangGraph 只保存待执行请求和等待/停止状态，不自行计算租户可用量。规划、正常回答、纠偏、格式修复、摘要、独立 Query Rewrite，以及受控的嵌套模型调用都必须纳入同一 Run 账本。复用现有模型决策生成辅助查询时只记该次真实模型调用，不虚构第二次消耗；Embedding/Rerank 若有 Token 用量，必须经对应出站适配器纳入明确的资源类别和预算策略，不能因藏在 RAG 工具内漏算。外部 MCP 内部未上报的模型消耗标为不可观测，不能声称已覆盖；要求完整硬限额的路径不得依赖不受控的隐藏调用。

**超额、等待与恢复。**Run Token 预算耗尽与调用次数耗尽一样：阻止新增消耗，持久记录停止原因，经现有无模型收尾结束或转人工，不再花 Token 生成总结。租户可续期周期额度不足可持久等待到下一 eligible 时刻，但必须有确定的周期规则且不超过原 Run deadline；恢复后重新检查当前额度。额度被在途预留暂占的情况应区分“等待结算”与“周期已消耗”，不能把每次拒绝都认定永久耗尽。任何等待都不延长 deadline、不重置 Run 累计量；已发请求可能仍消耗 Token，停止不等于远端立即取消。

周期切换时，旧请求的结算归属其预留时确定的 bucket，旧 bucket 保留至可对账，不能把晚到 usage 丢弃或随意转嫁新周期。周期重置不重置 Run 预算，也不冒充供应商独立的 TPM 限制。全局 Token、次数、deadline 等独立限制任一不满足，均不能继续出站。

**交付与验收。**先补 Provider 用量状态、归一化与完整出站覆盖，再实现数据库预留/结算账本和并发测试，然后接入配置/API/前端、等待/停止协议及审计，最后灰度启用严格模式。旧 Run 缺完整用量时不能从零回填后继续声称硬限额；须排空、可信迁移或明确限制为兼容模式。

必须覆盖：并发争抢、同 ID 重放、真实重试、发送前崩溃、发送后结果未知、流式中断、缺失 usage、估算偏差、缓存/推理子字段不重复累计、跨 Attempt/恢复不清零、迟到结算、周期边界、共享账户归并、调低配额、撤权、deadline 先到、无模型收尾，以及嵌套 RAG/改写调用不漏计。报告区分已报告、估算、未知与超额事件；Token 限额、费用限额、并发和模型上下文窗口分别验收，不混成一个“资源已受控”的结论。

### 两类执行边界（当前修订）

1. **短执行片段**：LangGraph 在安全调用边界检查单片调用次数和单调时间预算。已发出的请求必须完成、保存回执或明确失败后才让出；不存在“HTTP 尚在执行，保存 Checkpoint 后就交给另一个 Worker 重发”的安全捷径。次数是硬界限，时间是协作式阈值，不是线程强杀；单次外呼另有 deadline，片段耗时可能超过阈值一个在途调用的时间。
2. **长等待**：额度不足、退避、人工或外部异步任务应保存等待原因、恢复条件和 Checkpoint，返回并释放执行槽位/检查点连接。当前协议已接 QUOTA/RETRY/SLICE；人工和外部任务回调尚待专门契约，不能伪装成普通计时重试。

资源不可混用：异步 I/O 只减少线程等待成本；Worker 槽位保护本机活跃图；调用 Permit 保护远端在途负载。普通 HTTP 没有持久任务 ID 时，不能因本机超时或执行代次变更就释放外呼额度。若供应商提供持久任务 ID，再设计提交、结果查询/回调与恢复协议。

### V67 已落地及明确限制

- `JdbcGraphExecutionStore.reserve` 仍检查图后端 outstanding 子额度。V68 另以同事务 AFTER 触发器覆盖全平台 NATIVE/LANGGRAPH Run 创建、终态重试和终态释放；PAUSED/图等待不释放。全局/租户计数竞争串行化，事务回滚与冲突 no-op 不计费，超额返回 429。迁移锁住 Run 写入并在迁移事务显式建立可信 RLS 上下文后回填，防止并发漏计或非超级用户看不到完整基线。触发器权限/锁顺序及限额配置见手册；它不等于原生在途调用也被图许可覆盖。
- `claimNext` 只在调用方有本地空位时使用；同一数据库内按平台/租户活跃租约上限串行决策，再按持久化 `last_dispatch` 等份轮转。跳过无到期任务/饱和租户；候选行被锁时推进轮转，下一次有限扫描可服务其他租户。当前不冒充加权配额、管理预留和等待时长 SLO。
- 资格与外呼共享短事务锁序为 **策略行 → Run 行**，不在事务内调用模型或工具；全局计数入口要求 system-worker 权限，拒绝在租户 RLS 视图下计算所谓全局额度。V67 回填旧图租户轮转项，V65/V66 不修改。
- `GraphCapacityGateway` + `JdbcGraphCallCapacityStore` 按全局/租户/可信资源键一次性取得所有调用额度；未配置账户/连接器资源时拒绝，不退化成无上限。资源键解析器由可信部署装配提供，必须把共用凭证账户的多个 Provider 归并，不能直接拿 Provider ID 当物理账户。当前模型/工具 Gateway 调用采用保守外呼包络，尚非所有嵌套 Embedding/Rerank 的精确物理请求计数。
- ACTIVE 与 QUARANTINED 均计额度。成功返回可结算自己的 token；任何不确定失败保守隔离；孤儿扫描只分类，不释放。可信回执只读恢复不申请外呼额度，重新授权成功后以回执关联结算；人工/远端取消核对通过受信 reconciliation 入口记录依据，不允许浏览器传一段字符串就释放额度。
- `BoundedGraphWorker` 只有 slots 个 Future，不预取已领取命令；慢 RPC 保留槽位，poll 负责有限续租，续租失败后本地阻止后续调用，服务器继续校验代次。图持久挂起后先关闭 PostgreSQL 会话，再提交 defer/ack；丢交接 ACK 后以最新图状态恢复，而非相信旧命令的恢复游标。正常让出不生成 Attempt。
- Worker 当前是有界同步适配，不是已经完成异步 HTTP；活跃图最多各持有一个检查点连接。部署必须满足 `本机 slots ≤ 检查点连接预算`，并为控制面/JDBC 留独立余量。poll 周期、单次控制 RPC 超时和租约必须共同配置；这不是可忽略心跳调度的后台线程池。

### V68 装配与权限

Java 内部链只开放已声明的 POST 协议，dispatch 使用独立 Worker 凭据，gateway 使用租约 capability，均不复用浏览器/普通服务认证。图宿主按冻结 artifact 领取；Python CLI 驱动 poll/批量续租，每轮最多一条 claim，控制面 RPC 有界，失租停止后续外呼。未知命令能力不能访问工具引用。

管理 API 只允许平台管理员且保留 CSRF；资源从 AgentVersion 的 Provider 或已发布 MCP 快照的连接器反查。多租户/多个逻辑 Provider 可以映射同一物理账户。配置与许可领取共用策略锁；有未结算许可禁止换绑，配置及 append-only revision 审计同事务提交。图接管和调用锁序为策略行→Run；V68 状态变更触发器只取得独立的 admission 计数锁，不反向取得图策略锁。业务事务不得在取得 Run/admission 锁后反调需要图策略锁的路径。

仍未实现：AgentVersion 后端发布路由与最终业务接纳、可信未知外呼运维对账、全部策略统一版本化、加权/预留、全物理外呼/费用计数及真实容量报告。原生 Worker 的活跃竞争约束仍按本文件第一节记录，不能用全平台接收准入宣称它已被替换。
- 新组件仍不自动注册业务 Bean。认证 dispatch HTTP 客户端/宿主、artifact 路由、启动恢复、运维查询、策略版本化/审计及真实压测尚待接通。已有 MCP Redis 保护没有移除，统一启用前需明确包络/物理请求双层限额及嵌套死锁边界。

- 目标 Python Worker 使用受限异步 I/O或有界执行槽；Java 网关可用受控虚拟线程承载网络等待。当前契约模块的 `advance()` 是同步调用，活跃调用占一个检查点数据库连接但非长事务；不能将其测试吞吐当作已完成异步扩展。两侧均保留连接/在途/字节/CPU 上限，异步不等于无限并发。
- 长限流退避、人工等待等持久化后让出；外呼仍在远端运行时不能释放对应远端容量。耗时解析有输入上限或隔离 CPU 池，不假定软超时能强制抢占。
- 三种所有权分开：Java 命令投递租约、runtime 数据库会话独占权、Gateway 调用许可。投递租约过期只允许重投/对账，不允许 Java 接管图内位置；活跃数据库会话不以 TTL 强抢，失联释放时间须测。任何本地所有权丢失都不直接证明远端调用停止。
- 原生旧 Run 的 Heartbeat/Recovery 保留到排空；对新后端不重复注册原生 Run 心跳。平台 session generation 保护平台调用和业务提交，runtime 自身还须保证迟到检查点不能污染恢复。
- deadline 覆盖排队、暂停、退避和重试；跨服务传递绝对截止时间，各进程重新计算剩余并使用单调时钟消耗预算，不能转传本机 monotonic 时间戳。时钟同步、偏差容限与平台最终截止校验纳入部署测试。
- 摘要、路由、Embedding、Rerank、JSON 修复同样计入调用及费用；网关嵌套调用区分业务操作与实际外呼，避免同一父级容量重复扣减或持有全部父许可再等待自身子许可的死锁。

## 六、观测与验收

低基数指标覆盖接收/拒绝、outstanding、可调度等待 P50/P95/P99、runtime 排队与执行、调用 Permit/隔离额度、各类等待/限流/熔断、调用/Token/费用、取消/迟到/重复拒绝、对账积压及状态差异。Run、thread、operation 等高基数关联放 Trace/日志和受权限控制的运维查询，不直接作为无限指标标签。

运维须能区分“业务已接收”“图排队”“额度等待”“人工等待”“外呼中”“结果未知”“后端已完成但业务尚未接纳”；错误不能统一显示运行中或要求盲目重试。

G2 工程容量目标统一见[接入设计](langgraph-runtime-adoption-design.md#8-实施与替换门禁)，不另造冲突数值。强制验收：

1. 双实例抢最后一个平台/租户/共享供应商额度，任意时刻硬上限不超；政策缩容、数据库/Redis 故障及未知请求隔离。
2. 大租户突发、慢 Provider 与独立快 Provider 共存；可运行租户不饥饿，图队列、线程、连接和等待登记均有界。
3. 提交/挂起/resume 每个跨服务窗口丢 ACK、重复消息、强杀与网络分区；不丢任务，不双跑，不把正常 resume 计失败 Attempt。
4. 旧 Worker 复活不能新增外呼、污染图 Checkpoint 或完成业务；仅测 Java 迟到结果拒绝不够。
5. 已成功工具回执与已持久化候选恢复不依赖模型重答；模型响应未保存的未知窗口单列重复成本。
6. P-17 七场景、同租户双采购、连续压缩、JSON 修复、撤权和跨 Run 引用均不退化。

执行顺序：先推进 G0/G2 共有的容量契约、预算片段/持久等待、治理与有界派发闭环；再并行完成 G1 节点迁移/业务等价和 G2 多实例压力报告；最后 G3 切换/排空。不等全部路由/压缩节点迁移完才治理并发，也不把全部节点拆成队列任务。当前尚未通过这些门禁，不能因选择 LangGraph 或启用虚拟线程就宣称生产高并发已完成。
