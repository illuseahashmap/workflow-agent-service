# Workflow Agent 开发方向与防偏离门禁

更新时间：2026-08-24  
状态：长期技术方向约束

本文不重复定义跨仓库产品定位。产品定位、目标用户和阶段目标以聚合仓库的
[《Workflow Agent 产品定位与目标》](https://github.com/illuseahashmap/workflow-agent/blob/main/docs/product-positioning-and-goals.zh-CN.md)
为唯一权威来源。本文只回答后端后续应当建设什么、哪些边界不能突破，以及如何判断一项
新能力是否偏离主线。

## 1. 技术方向

后端的长期目标不是复制 Flowable Enterprise 或 Dify，而是在 Flowable OSS 的执行原语之上，
建设面向多租户企业场景的工作流业务层和受治理 Agent Runtime：

```text
Flowable：流程、任务、长期状态和历史事实
Workflow Agent：企业审批语义、人机协作治理和可靠 Agent 执行
Dify 等参考项目：Provider、工具、知识、评测和产品交互经验
```

“支持 Agent 节点”或“支持人工复核”本身不是差异化。Flowable Enterprise 已具备相近方向，
项目的长期价值必须落在以下组合闭环：

> 开源 Flowable 平台化封装 + 企业审批业务语义 + 可持久化 Agent Runtime +
> 证据驱动的渐进式自治 + 可验证的人机协作流程生成。

## 2. 三条必须持续收敛的主线

### 2.1 企业工作流业务层

平台应向业务系统提供稳定的领域命令和查询，而不是直接暴露零散 Flowable API。重点包括
审批、退回、转办、会签、参与人、表单、任务中心、审计、SLA、通知和异常恢复。

Flowable 始终是流程状态的唯一权威。本项目复用其执行语义，不重新实现 BPMN 引擎、任务
状态机或历史系统。

### 2.2 受治理的人机协作与渐进式自治

Agent 不应固定为“只能建议”或“一律自动完成”。平台通过真实运行证据，让 Agent 在特定
租户、流程、任务类型和风险范围内从观察逐步升级：

```text
HUMAN_ONLY
→ SHADOW
→ ADVISORY
→ SUPERVISED
→ CONSTRAINED_AUTONOMOUS
```

模型自报置信度不能单独决定完成权。一次任务是否允许自动推进，至少同时受到以下约束：

- BPMN 声明的自治上限；
- 租户安全策略和任务风险等级；
- AgentVersion、模型、Prompt、知识和工具版本；
- Schema、业务规则、Guardrail 和 Grounding 结果；
- 工具调用结果及引用证据完整度；
- 历史人工接受率、修改率、推翻率和下游业务结果；
- 样本量、数据切片覆盖、灰度范围和回退条件。

平台形成的是确定性治理决策，而不是让另一个模型自由判断是否可信：

```text
AUTO_CONTINUE  自动推进
HUMAN_REVIEW   人工复核
RETRY          重新执行
FALLBACK       降级处理
BLOCKED        阻断流程
```

高风险操作必须保留人工或确定性规则授权。自治等级可以自动降级、冻结或转人工，不能在没有
足够证据和审批的情况下自动扩大权限。详细领域模型和运行语义以
[《证据驱动的 Agent 渐进式自治设计方向》](evidence-governed-agent-autonomy.md)为准。

### 2.3 可验证的人机协作流程生成

流程生成器不是“让大模型直接输出一份 BPMN XML”，而是生成包含人工、规则、Agent、知识、
工具、异常路径和测试报告的协作流程发布候选：

```text
业务描述
→ 需求抽取与歧义确认
→ 版本化语义 IR
→ 流程骨架
→ 节点与治理细节填充
→ 确定性 BPMN 编译和布局
→ 静态校验、场景测试和 Agent Eval
→ 受约束修复
→ 人工审阅与发布
```

生成能力只能产生可编辑草案，不能绕过权限和测试直接修改生产流程。

## 3. Agent Runtime 的稳定扩展边界

所有 Agent 执行模式必须复用同一套运行账本和可靠性语义：

- `AgentDefinition` 与不可变 `AgentVersion`；
- `AgentRun / Attempt / Step / Checkpoint`；
- Lease、Heartbeat、Recovery、幂等和迟到结果隔离；
- Outbox/Inbox、失败重试、死信和人工恢复；
- Schema、结果策略、证据、预算、审计和指标。

`MODEL_ONLY`、`PLATFORM_AGENT` 和未来 `REMOTE_AGENT` 只能扩展执行器和能力端口，不能各自
建立独立状态机、任务表或 Flowable 恢复协议。

## 4. RAG、MCP、知识库与新技术的位置

RAG、MCP、OpenAPI、远程 Agent、缓存和多 Agent 都是可替换的 Agent Capability，不是项目
定位本身：

```text
Agent Capability
├── Knowledge Retrieval
├── MCP Tool
├── Governed HTTP API
├── Workflow Context
└── Platform Built-in Tool
```

新增能力必须复用租户、权限、版本、凭据、预算、审计、幂等、超时和结果策略。模型只能看见
本次运行明确授权的能力 Schema，不能读取凭据，也不能构造未经治理的任意网络或代码调用。

新框架只有在明显降低复杂度、提高互操作性或补齐已验证能力缺口时才可引入。不得为了展示
新技术破坏现有领域模型、事件协议和恢复语义。

## 5. 明确不进入核心路线的内容

- 自研流程执行引擎或复制 Flowable 已成熟的底层能力；
- Dify 类通用 AI 应用画布和插件市场；
- 无约束的多 Agent 自主协商；
- 租户上传任意 Java、脚本或可执行插件；
- 使用 Prompt 代替权限、业务规则和安全策略；
- 模型直接调用 Flowable API 修改流程状态；
- 没有真实业务场景、故障测试和验收指标的功能堆叠。

## 6. 开发优先级

后端能力原则上按以下顺序推进：

1. 关闭租户、安全、事务、可观测性和故障恢复的生产基线问题。
2. 完成工作流业务语义和 Agent Service Task 的可靠纵向闭环。
3. 完成受治理工具、结果策略、人工接管和运行证据。
4. 落地 `SHADOW`、`ADVISORY`、人工反馈和历史评测。
5. 在证据充分时逐步实现 `SUPERVISED` 和低风险受约束自动完成。
6. 完成语义 IR、确定性 BPMN 编译、测试和修复闭环。
7. 按代表性业务案例需要扩展 RAG、MCP、知识库和连接器。

下一阶段不能以牺牲前一阶段的版本、权限、审计和恢复语义为代价。性能优化、缓存和模型路由
只能替换基础设施策略，不能改变业务结果契约。

## 7. 功能准入门禁

任何新增平台级能力在进入实现前必须回答：

1. 它解决了哪个明确的企业工作流或人机协作问题？
2. 为什么应由 Workflow Agent 解决，而不是直接复用 Flowable、Dify 或外部服务？
3. 它属于工作流领域、Agent Runtime、治理层还是外部适配器？
4. 它如何处理租户、权限、版本、凭据、预算和审计？
5. 它如何处理幂等、超时、失败、重试、恢复和迟到结果？
6. 它是否增强运行证据、人工接管或自治决策闭环？
7. 它能否进入代表性业务案例并形成自动化验收？
8. 删除该能力是否会损害项目的一句话定位？

无法清晰回答时，该能力不进入近期核心路线，只能停留在实验或长期预留中。

## 8. 代表性验收闭环

项目应长期维护至少一个可复现的企业案例，例如合同审核、采购申请或服务工单：

```text
材料提交
→ Agent 提取和分析
→ 知识检索或企业工具核验
→ 保存结构化结论、证据和运行版本
→ 自治策略判定
→ 自动推进、人工复核或人工接管
→ 保存人工纠正和下游结果
→ 评估 AgentVersion 质量并支持安全降级
```

案例必须覆盖 Worker 重启、Provider 超时、工具失败、空结果、部分结果、重复事件、迟到结果、
越权调用和跨租户访问。只有功能、运行证据、故障恢复和人工责任边界同时闭环，才能作为
生产导向能力对外说明。

## 9. 方向完成标准

项目是否成立，不以代码量、模型数量或功能数量衡量，而以以下结果衡量：

- 业务系统无需理解 Flowable 内部 API 即可使用主要工作流语义；
- Agent 执行可治理、可恢复、可审计并能安全调用受控能力；
- 人工能够查看证据、确认、纠正和接管；
- 自动完成权由版本化证据和风险策略决定，而非模型自报置信度；
- 流程生成结果可解释、可修改、可测试并经过人工发布；
- 新技术能够通过稳定端口接入，不破坏已有可靠性和业务边界。

当前完成状态仍以[下一步计划](../status.md)和[待修复问题](../quality/known-issues.md)为准，
本文中的目标能力不得被描述为已经实现。
