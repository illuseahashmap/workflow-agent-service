## §1 适用范围与流程原则

本规程描述普通办公采购从申请到验收关闭的操作步骤；服务订阅、生产系统、安全敏感采购或合同另有要求的事项，须先由采购管理负责人确认适用政策。申请、预算、合同、订单、验收、付款是分离的业务对象，**不能因为界面上都显示“已完成”就视为同一事实**。每个对象都应保存稳定业务 ID、操作人、时间、版本和关联证据。

采购工作流只负责记录授权决策与推进任务，不可根据 RAG 答复自动选定具体审批人员。人员从可信组织系统、角色授权和流程派单规则获取。模型可以解释制度和提示缺失材料，但不能代替组织任职判定、预算记账、合同签署或付款执行。

## §2 申请资料与准入检查

### §2.1 必填信息

申请人填写：采购用途、受益部门或项目、采购类别、数量/规格、期望交付日期、预计含税总对价、费用组成、币种、成本中心、预算来源、拟供应商、是否为已有合同的续购/增购、是否涉及客户数据/生产系统/跨境履约，以及与既有申请的关联 ID。未取得正式报价时，应标明估算依据和可执行封顶金额；不能同时填“金额待定”并请求按最低档审批。

附件包括有版本和日期的报价/询价记录、需求说明，以及必要的供应商与预算材料。附件中不得放真实登录凭据、个人身份证件或未授权客户资料。若有同类订单，需列明是否为独立需求；“找不到历史订单”不等于不存在相关采购。

### §2.2 受理前校验

采购运营核对分类、字段完整性、§2.1 附件、`PROC-POL-01 §2` 的金额与拆单口径、供应商准入状态和重复申请风险。缺少确定金额、用途或预算归属时退回补充，保留原申请 ID 和退回原因；不得创建新申请绕过历史轨迹。采购运营可以提出分类意见，但如果涉及政策争议，交采购管理负责人裁定并留痕。

## §3 流程节点和状态

表 1：普通办公采购从草稿到关闭的状态及证据。此表是步骤索引，具体能否继续须同时满足各条文字规则。

| 阶段 | 输入/必备证据 | 负责角色 | 完成标志及下一步 | 不能推断的事实 |
| --- | --- | --- | --- | --- |
| 草稿与提交 | §2.1 字段、附件 | 申请人 | `SUBMITTED`，生成申请 ID | 尚未获得任何审批。 |
| 受理和分类 | 类别、金额计算、关联采购检查 | 采购运营 | `ACCEPTED` 或 `RETURNED_FOR_INFO` | 受理不等于批准。 |
| 业务审批 | 按有效政策决定的直属/部门负责人 | 有权审批人 | 所需人均同意后 `BUSINESS_APPROVED` | 部分同意不等于全部同意。 |
| 大额复核 | 预算、供应商与委员会触发资料 | 财务中心、适用时采购委员会 | `BUDGET_CLEARED`；适用时 `COMMITTEE_APPROVED` | 预算复核不是支付批准。 |
| 下单前门禁 | 全部审批、有效报价、合同/授权、预算 | 采购运营及相关职能 | `READY_TO_ORDER`，记录门禁快照 | 可以下单不等于供应商已接受。 |
| 订购和交付 | 订单/合同、交付单 | 有权下单者、收货人 | `ORDERED` → `DELIVERED_PENDING_ACCEPTANCE` | 已到货不等于验收通过。 |
| 验收与关闭 | 数量/质量/服务记录、差异处理 | 需求方与采购运营 | `ACCEPTED_DELIVERY` → `CLOSED` | 已验收不等于财务已付款。 |

状态顺序不能用“最近一条审计事件”推断；同一申请可能退回、重提、部分交付或撤销。每次重提都要关联原申请及版本。上表中的状态名是**拟议文档词汇**，尚未声明已与当前 Flowable/BPMN 枚举或 API 一一对应；实际接入前须做映射审查。

### §3.1 业务审批

根据当时有效的采购政策计算金额档位：不超过 2,000 元由直属负责人审批；超过 2,000 元但不超过 20,000 元由直属和部门负责人共同审批；超过 20,000 元还需财务中心复核预算，并在满足委员会触发条件时进入委员会。对于流程引擎，只有所有必需分支成功汇聚，才能继续下单前门禁；某一路驳回或待补资料时不得把另一分支的通过当作整体通过。具体人员 ID 以任务激活时可信组织数据和派单规则为准。

审批人若为同一自然人兼任两个职务，是否允许一人完成两类审批属于岗位分离策略，不能仅因为账号相同自动合并任务；此规程草稿不作授权结论，须由已批准的职责分离矩阵或人工合规复核确定。委托审批只在有效授权范围和期限内生效，代理关系需有审计记录。

### §3.2 预算、委员会与合同

财务中心收到大额申请时核对预算年度、成本中心、预算类别、可用额度及报价；预算不足可退回调整、申请预算追加或拒绝，不能用“已通过业务审批”覆盖。采购委员会触发资料缺失时标记待核验，不得以空值解释为“不触发”。如果需要合同/用章，采购运营必须取得法务和授权签署结果；审查通过但未签署，不能标记合同已生效。

### §3.3 下单、验收与付款衔接

下单人核对当前报价与批准快照的一致性，记录供应商、订单总价、订单版本和合同引用。订单数量、费用组成或范围变更按 `PROC-POL-01 §4.2` 重新核对，跨档则补审批；不能仅改发票或订单备注。收货人按订单逐项核对数量、规格和损坏情况；部分交付记录已交付数量与待交付余额，不得整体标记为已验收。财务付款/员工报销由财务规程另行核验票据、业务真实性、重复支付和合同约定；采购关闭不产生自动付款指令。

## §4 异常、撤回和紧急路径

### §4.1 退回、驳回与撤回

资料不完整时使用退回补充，列出缺失字段和引用条款。审批人不同意业务必要性时记录驳回原因，重新申请不能清除原审计轨迹。申请人在下单前可申请撤回；若已向供应商形成承诺或已交付，不能把“撤回流程”理解为合同自动解除或费用消失，须由采购和法务处理后续义务。

### §4.2 报价失效、供应商变化和拆单疑点

报价过期或供应商改变时，重新核对价格、准入和合同风险；超过已批准条件则重新审批。发现可能拆单时暂停下单、关联申请并提交采购管理负责人；调查前不得自动定性违规，也不能让多个低额申请并行通过以规避政策。处理结论写入申请审计，而不是只写在聊天记录中。

### §4.3 紧急采购

申请人说明紧急原因、停等损失、替代方案、需要的最晚决策时间。采购负责人确认是否进入紧急流程，财务/法务/安全按各自职责参与；只有明确授权的角色能批准先行承诺，且应记录批准范围、上限、时间与后补材料。**本草稿尚未定义紧急审批时限和缺席代理规则**；在规则批准前必须人工处理，Agent 不得编造“24 小时内补单”等数字。

### §4.4 供应商拒绝、验收不合格和重复付款风险

供应商拒绝订单时不等于采购申请失败，采购运营应更新订单状态并确认是否重新寻源/审批。验收不合格时记录缺陷、退换/折让方案和合同依据；不得用“已到货”替代验收。发现已支付或已报销相同费用时交财务核查，采购运营不自行做会计冲销。

## §5 审计、证据与交接

每次状态变化至少记录：申请 ID、关联订单/合同/发票 ID、原状态和新状态、业务动作、操作者可信身份、发生时间及失败原因；审批结论还应记录审批角色、授权快照和所依据的申请版本。Trace ID 可以帮助定位系统执行，但不是业务审批证据本身。日志和附件不保存密钥、完整令牌或不必要个人信息。

向财务交接时提供已批准申请版本、订单与验收引用、实际金额和差异说明；向法务交接时提供合同/供应商/特殊条款；向运维报告系统故障时提供申请 ID、流程实例 ID、时间与 Trace ID，不粘贴敏感材料。需要回答“现在能否下单/付款”的检索问题时，必须分别检查当前状态和适用政策；只有文档规则而无实时业务状态时，应说明无法判断这笔真实申请。

## §6 流程图需求与版本限制

本规程的**主要流程目前用 §3 的编号步骤和表 1 表达**。未来若制作流程图，适合绘制“分类→金额分支→并行/顺序审批→预算和合同门禁→下单→验收→付款交接”的 SVG/PNG，并把所有网关条件、拒绝/退回路径和汇聚规则以同一章节文字呈现；图不能新增正文没有的审批条件。当前知识摄取尚不解析图片，也不保证 Markdown 表格的结构化行列语义，故未把图片作为唯一事实源。图发布前须满足[文档编写与多模态扩展规范](../../../../architecture/rag-document-authoring-standard.md)的资产、替代文本、版本和授权检查。

## §7 发布前检查

采购运营负责人需确认真实表单字段与状态映射，财务确认预算和付款交接，法务确认合同与紧急授权边界，平台团队确认 BPMN 分支/汇聚和权限执行语义。本文与 `PROC-POL-01` 均为草稿，正式发布时应冻结依赖版本并填入审批与生效信息；任何无法映射或缺乏政策依据的步骤应从自动执行路径移除，保留人工处理入口。
